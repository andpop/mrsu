# Лабораторная работа 6. Автоматизированное функциональное тестирование веб-сайта с помощью фреймворка Selenium

### Цель работы
Научиться автоматизировать функциональные проверки веб-приложений с использованием Selenium IDE или Selenium WebDriver. Закрепить навыки написания поддерживаемого, независимого и читаемого автоматизированного кода, минимизирующего затраты на его дальнейшее сопровождение.

> **Примечание:** В данной работе ИИ-ассистенты (Qwen, DeepSeek, GitHub Copilot и аналоги) выступают в роли «Pair Programmer» (парного программиста) и «Code Reviewer». ИИ отлично справляется с рефакторингом «грязного» кода, генерируемого рекордерами, и поиском оптимальных локаторов, но **архитектура теста, выбор проверяемых сценариев и финальная валидация логики** остаются за вами.

### Задания
Необходимо автоматизировать выполнение тестов функциональности сайта из предыдущего задания (Лабораторная работа 5). Для автоматизации использовать плагин Selenium IDE или написать скрипт, подключающий библиотеку для управления браузерами Selenium WebDriver (на языке Python).

Составить отчет о тестировании, содержащий следующие разделы:

* **Описание предмета тестирования**. Необходимо описать сайт, который будет тестироваться в рамках лабораторной работы. В описании указывается, для чего сайт предназначен и какие основные функции для пользователя он выполняет.
  > 💡 **Рекомендация по использованию ИИ:** Попросите ИИ оценить выбранные сценарии на предмет целесообразности автоматизации.
  > *Пример промпта:* «Я планирую автоматизировать следующие сценарии для сайта [URL/Описание]: [список сценариев]. Оцени их с точки зрения ROI автоматизации. Укажи, есть ли среди них те, которые лучше оставить для ручного тестирования из-за высокой хрупкости, субъективности проверки или высоких первоначальных затрат?»

* **Описание окружения тестирования**. Необходимо описать характеристики компьютера, используемое ПО (ОС, браузер, версии драйверов), а также инструмент для автоматизации тестирования (Selenium IDE / Selenium WebDriver + Python + pytest и т.д.).

* **Тест-кейсы**. Описываются несколько позитивных и негативных сценариев. Для каждого сценария привести листинг кода для выполнения тестов.
  > 💡 **Рекомендация по использованию ИИ (Ключевой этап):** Если вы используете Selenium IDE для записи действий, экспортированный код будет содержать хрупкие XPath и хардкод. Используйте ИИ для рефакторинга.
  > *Пример промпта:* «Я экспортировал этот код из Selenium IDE: [ВСТАВИТЬ КОД]. Перепиши его на Python с использованием Selenium WebDriver и pytest. 
  > Правила рефакторинга:
  > 1. Замени хрупкие XPath-локаторы на более стабильные (CSS-селекторы, data-атрибуты или текстовые соответствия).
  > 2. Замени все неявные ожидания (`time.sleep`) на явные ожидания (`WebDriverWait` и `expected_conditions`).
  > 3. Вынеси повторяющиеся значения (URL, тестовые данные) в константы или фикстуры, чтобы избежать хардкода.
  > 4. Сделай тесты полностью независимыми друг от друга (каждый тест должен уметь запуститься первым).
  > 5. Добавь подробные docstring, описывающие тест как миниатюрную техническую спецификацию.»

* **Логи и результаты автоматического тестирования**. Описывается выполнение сценариев с приведением скриншотов (или логов консоли) и описанием результата этого действия.
  > 💡 **Рекомендация по использованию ИИ:** При возникновении ошибок выполнения (например, `NoSuchElementException` или `StaleElementReferenceException`), используйте ИИ для анализа причины.
  > *Пример промпта:* «Мой автотест на Selenium падает с ошибкой [ВСТАВИТЬ ТРЕЙСБЕК ОШИБКИ] на шаге [ОПИСАНИЕ ШАГА]. Предложи 3 наиболее вероятные причины (например, динамическая загрузка DOM, iframe, изменение локатора) и покажи исправленный фрагмент кода с использованием явных ожиданий.»

> 🎓 **Советы от преподавателя:**
> 1. **Борьба с хрупкостью (Flaky Tests):** Самая частая причина провала автотестов в Selenium – попытка взаимодействия с элементом, который еще не отрисовался или уже изменился в DOM. Никогда не используйте `time.sleep()`. Всегда используйте `WebDriverWait` в связке с `expected_conditions` (например, `element_to_be_clickable`). Попросите ИИ показать примеры именно такого подхода.
> 2. **Идеология независимости:** Каждый автотест должен быть «островком». Он не должен зависеть от того, что предыдущий тест оставил пользователя залогиненным или добавил товар в корзину. Используйте фикстуры `pytest` (например, `@pytest.fixture(autouse=True)`) для очистки состояния (очистка cookie, localStorage или сброс БД) перед каждым запуском.
> 3. **Универсальность взаимодействий:** Избегайте привязки к визуальным координатам или абсолютным XPath вида `/html/body/div[2]/div/span`. Стремитесь к локаторам, которые переживут редизайн: `By.CSS_SELECTOR, "[data-testid='submit-button']"` или `By.ID`. Это главный способ снижения затрат на поддержку автотестов в долгосрочной перспективе.
> 4. **Техническая детализация:** Ваш автотест – это исполняемая спецификация. Имя тестовой функции должно быть информативным: `test_login_with_invalid_password_shows_error_message()`, а не `test_1()`.
